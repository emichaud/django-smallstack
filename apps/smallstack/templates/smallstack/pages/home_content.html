{# ── WHAT YOU CAN BUILD ON IT ───────────────────────────────────── #}
What you can build on it
Internal tools

A themed admin shell with CRUDView pages, the Explorer, user management, activity and audit logs. The ops tool you would otherwise build from scratch.

API backends

REST with Bearer auth, an OpenAPI 3.0.3 schema, Swagger UI and ReDoc, plus typed TypeScript and Python clients for your React, Svelte or Streamlit frontend.

MCP servers

JSON-RPC + OAuth 2.0 + PKCE. Claude Desktop and the Claude.ai Connectors UI connect with no setup, and every opted-in model becomes a set of tools.

Integration hubs

Signed outbound webhooks on model change, verified inbound receivers, RSS/Atom publish and consume, and SmallStack-to-SmallStack pairing.

Workflow apps

Recurring @scheduled jobs on a DB-backed worker, human-in-the-loop approvals with a decision console, and in-app notifications with a topbar bell.

Publishing

Versioned runbook documents, per-user blogs with a writing studio, a public reading surface with feeds, and a durable newsletter sender.

{# ── ONE MODEL → EVERY SURFACE (the killer feature) ─────────────── #}
The pipeline

One model. Every surface.

Define your model once. CRUDView's opt-in flags emit the same form, queryset and permission logic as an HTML admin page, a REST endpoint, MCP tools, a search index, webhook events and a feed — each wired through the same tenancy hook, and all of them reachable from the terminal. 

# apps/support/views.py
class TicketCRUDView(CRUDView):
    model           = Ticket
    actions         = [Action.LIST, Action.CREATE, Action.DETAIL, Action.UPDATE, Action.DELETE]
    filter_fields   = ["status", "priority", "customer"]
    search_fields   = ["subject", "body"]
    enable_explorer = True     ───→  HTML      /smallstack/explorer/support/ticket/
    enable_api      = True     ───→  REST      /api/tickets/ · OpenAPI · typed clients
    enable_mcp      = True     ───→  MCP       list_tickets, get_ticket, create_ticket, …
    enable_search   = True     ───→  SEARCH    /search/ · search_tickets
    enable_webhooks = True     ───→  WEBHOOKS  ticket.created / updated / deleted, signed
    enable_rss      = True     ───→  FEED      /feed/<slug>.rss · .atom
                                      CLI       sc ls support.Ticket   (always on)
HTML

REST

JSON with Bearer tokens, search, filter, ordering, FK expansion, aggregation, exports.

MCP

/mcp · tools/list

JSON-RPC + OAuth. Claude Desktop and Connectors UI work without extra setup.

Search

/search/ · search_all

Full-text index across your models, runbooks, blog posts and the help docs — also an MCP tool.

Webhooks & feeds

/smallstack/webhooks/

Signed deliveries with retries and dead-letter replay, inbound receivers, RSS/Atom for any model.

CLI

sc ls · get · new · set

Terminal CRUD over every registered model, with the same validation and audit trail as REST and MCP.

{# ── PLATFORM SEAMS ─────────────────────────────────────────────── #}
Build on it

The seams the built-in apps use are yours too.

Nothing in the shipped apps is special-cased. Your app registers through the same hooks, so it gets the same navigation, dashboard, status page, docs and agent tooling the moment it does.

nav.register()

A sidebar or topbar entry from your AppConfig. No template surgery.

dashboard.register()

A widget on the /smallstack/ dashboard with live counts and a degraded state.

monitors

A Service + Monitor pair on the status page, with SLA-excluded maintenance windows.

@scheduled

Recurring work with a themed schedule UI, REST and MCP controls, and a per-minute tick.

@approval_kind

Gate any action on a human decision; react via callback, signal, webhook or polling.

notify()

An in-app notification for a signed-in user, with branded email fan-out.

@webhook_handler

Receive and verify inbound webhooks; provider signatures via @webhook_verifier.

@dataset

A filtered queryset as typed rows and columns for dashboards, reports and charts.

register_feed()

A curated RSS/Atom feed alongside the one-flag model feeds.

@tool

A custom MCP tool next to the generated ones, under the same OAuth and audit log.

help_content_dir

Markdown docs shipped with your app, rendered and searchable in the help system.

docs/skills/

Skill files that brief AI agents on your conventions; the index is generated and lint-checked.

{# ── SEARCH ─────────────────────────────────────────────────────── #}
Find anything

One index. Everything searchable.

A single full-text index spans your models, runbook documents, blog posts and the bundled help docs. A three-tier access model keeps staff-only data staff-only while public search stays open — and the same index backs a search_all MCP tool, so an AI agent queries your app the way a person would.

Public

/search/

An instant omnibar over your documentation and public content — open to anyone, no login required.

Gated

your models

Opt a model in with one flag; results respect each viewer's staff / auth access tier and your tenancy scope.

MCP

search_all

The same index as a tool — Claude searches across every source in one call.

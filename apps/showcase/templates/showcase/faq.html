Questions before you build

What can you build on SmallStack?

The questions people ask before choosing it, answered plainly, including where it isn't the right tool. Grouped by who is asking: someone deciding what kind of system to build, someone adding SmallStack's parts to an app of their own, and someone connecting it to other tools. For how-to questions (an admin user, a colour, a test run) see the help FAQ.

System builders

Is SmallStack a good base for the thing you have in mind: a blog, a website, an API server, a CRM, an app with a React front end?

What is SmallStack, in one paragraph?

A Django project you clone and build on. It ships a themed admin shell, accounts, and a set of working apps (a blog and newsletter, versioned markdown documents, dashboards, a calendar, approvals, notifications, uptime monitoring, logs, search, a scheduler), plus the plumbing they share. Its central idea: one CRUDView declaration on a model gives you the list, detail and form pages, a REST API, MCP tools for AI clients, search and outbound webhooks, each switched on with a flag. It's plain Django underneath, so anything you know about Django still applies.

Is it good for building a blog?

Yes, a blog is built in. Each user can run blog channels of markdown posts with a three-step visibility ladder (private, members, public), scheduled publishing, tags, archives and per-blog search. Readers get /blog/, RSS, Atom and JSON feeds for each blog, and an anonymous JSON read API. A newsletter rides on top: double opt-in, one-click unsubscribe, and a sender that survives restarts mid-send. Runbook documents can be published into a blog and kept in sync.

Not built in: comments, and a visual page builder. Writing is markdown. See Blogs & newsletters.

Can it be my public website or marketing site?

Yes. apps/website/ is yours to edit: the home page and any pages you add, on SmallStack's theme (six colour palettes, each in light and dark) with your branding from the BRAND_* settings. If you already have a design system (Bootstrap, Tailwind, a theme you bought), use your own base template instead; SmallStack's pages keep theirs. These showcase pages are an example, and a project deletes them when it starts.

It isn't a CMS: pages are Django templates edited in code, not in a browser editor. The blog is the browser-edited part.

Is it good for an internal tool or back office?

This is where it is strongest. A CRUDView gives you searchable, filterable list pages with bulk actions, CSV/JSON export, detail pages with related-record tabs, a delete confirmation that lists what cascades, and an audit trail with a History page. Explorer turns your existing Django admin registrations into the same kind of pages with no new code. Add dashboards and goals over your data, human approval steps, in-app notifications, scheduled jobs, and Django model permissions when staff need different access.

Can I build a CRM on it?

Yes, but there is no CRM app in the box: you write the models (contacts, companies, deals, activities) and give each a CRUDView. That one step gets you the pages, the REST API, MCP tools so an assistant can look up and update deals, and search across all of them. Then the built-in parts do the rest: a @dataset over deals feeds pipeline metrics, dashboards and goals; a calendar dataset puts follow-ups on the shared calendar; outbound webhooks tell your email or billing tool when a deal closes; an approval gates large discounts.

What you'd build yourself: email and calendar sync with Gmail or Outlook, and a drag-and-drop pipeline board.

Is it good as an API server?

Yes. enable_api = True on a CRUDView gives that model JSON list, detail, create, update and delete endpoints with search, filtering, ordering, pagination, related-object expansion, sum/average/min/max aggregation and CSV/JSON export. Every endpoint lands in an OpenAPI 3.0.3 schema with Swagger UI at /api/docs/ and ReDoc at /api/redoc/. Endpoints that aren't CRUD use the @api_view decorator and appear in the same schema. Clients authenticate with Bearer tokens, read-only or full access, managed from a page or the command line.

It's a JSON API, not GraphQL, and it isn't Django REST Framework, so DRF serializers and viewsets don't plug in.

Can I use it headless, behind React, Vue, Next.js or Svelte?

Yes. Your front end owns the UI; SmallStack is the backend: data endpoints from your CRUDViews, plus account endpoints for sign-in, sign-out, token refresh, the current user and password change. To set it up:

  • List your front end's origin in CORS_ALLOWED_ORIGINS.
  • Sign users in with POST /api/auth/token/; send the returned token as Authorization: Bearer ….
  • For sign-up, call /api/auth/register/ from your server with an auth-level system token. That token must never reach the browser, so a front end with no server side of its own can't offer sign-up safely.
  • Generate a typed client from /api/schema/openapi.json with a tool such as orval.

Worth knowing: each user has one login token at a time, so signing in again ends the previous session; there's no social sign-in or emailed password reset over the API. The staff side (logs, dashboards, the User Manager) keeps working beside your front end. See React + SmallStack.

What about a mobile app backend?

The same as headless: the app signs in for a token and calls the REST API. There's no push-notification service; in-app notifications exist for the web pages and have a per-user REST API you can poll.

Can I build an app for customers, where each sees only their own data?

Yes, but you decide the tenancy rule: there's no built-in tenant model. You write it once on each CRUDView, as get_list_queryset (for example, only rows whose owner is the signed-in user). The framework applies that rule to the list, every single-record page, REST, MCP, search and bulk actions, so a row hidden from the list can't be read or changed at its own URL. Row-level rules (can_update, can_delete) are enforced on every write surface too. Customers sign up, sign in by password or emailed code, and are invited by staff.

Can it do dashboards, KPIs and reports?

Yes. Declare a @dataset over a queryset and it can be browsed, charted, exported and queried. On top of datasets: metrics (a stored filter and an aggregate, including median), grid dashboards, KPI reports across periods, goal lists judged on target, at risk or missed, and calendars of anything with a date. An AI agent can build them through MCP. See Datasets & calendars.

Can it run an online shop or take payments?

Not on its own: there's no cart, checkout or payment integration. What it gives you is the inbound side: a webhook receiver that verifies Stripe's signatures (or GitHub's, or your own scheme) and hands each event to your handler, which is where a payment provider's notifications land. The checkout itself is your code or the provider's hosted page.

What is it not a good fit for?
  • Real-time apps such as chat or live collaboration: there are no WebSockets. Pages refresh by polling (the log viewer's live mode, for example).
  • A translated interface: Django's translation framework is on, but SmallStack's own pages are written in English only.
  • An editor-driven CMS with page layouts built in the browser.
  • Very high traffic on SQLite. SQLite is the default and handles a great deal; for many concurrent writers, switch to PostgreSQL, which is fully supported.
I already have a Django project. Can I add SmallStack to it?

Not easily, and we don't recommend trying. SmallStack is a platform rather than a package you install. Its settings, database configuration and middleware are tuned together for the platform, and an existing project has made its own choices for the same things:

  • Settings: its own user model (accounts.User, which Django lets a project choose only once), sign-in with lockout protection, a Content Security Policy that blocks inline JavaScript, background tasks, logging that feeds the log viewer, and about ninety SMALLSTACK_* switches.
  • Database: SQLite tuned for production (WAL mode, immediate transactions), a full-text search index the search app builds after each migrate, and a median function added to every SQLite connection.
  • Middleware: eighteen classes in a deliberate order (health checks, request ids, activity logging, htmx, lockouts, the security policy) that would have to be merged into yours without breaking either.

Reconciling all of that at once is where adoption goes wrong, and every setting changed to fit the old project conflicts again each time you take a SmallStack update.

What works is the other direction: start from a fresh SmallStack clone and move your apps into it.

  • Code: each of your Django apps moves into apps/ largely as it is. Your models, views, forms and templates keep working, because SmallStack is ordinary Django underneath.
  • Data: bring it across with dumpdata / loaddata, or a database-level copy for larger sets. Plan the users first: SmallStack has its own user model, so your accounts and anything pointing at them move together.
  • SmallStack's tools: adopt them where they earn their place, not all at once. A CRUDView replaces admin pages you'd otherwise maintain; enable_api, enable_mcp and enable_search add a REST API, AI tools and search to a model; a @dataset puts it on dashboards. Code that's fine as it is can stay plain Django.

The adopting-smallstack skill in docs/skills/ walks through the move step by step, users and data included. The help page Plain Django on SmallStack shows an app written that way. A coding agent can do much of the move, app by app; the prompts page shows how to brief one.

Components in your own app

How to use SmallStack's parts in an app you build on top of it, including one with its own look.

How do I add pages for one of my models?

Subclass CRUDView, name the model and fields, and include its get_urls() in your urls.py. You get list, detail, create, edit and delete pages on the theme. Add it to the sidebar with nav.register(). Turn on what else you need with flags: enable_api, enable_mcp, enable_search, enable_webhooks, enable_history, bulk_actions, model_permissions. Hooks such as get_list_queryset, can_update and on_form_valid apply on every surface at once. See Building CRUD pages.

Is there something quicker than a CRUDView for staff pages?

Explorer. Register a model with a Django ModelAdmin in your app's explorer.py and it appears at /smallstack/explorer/ with themed list, detail and form pages. It reads the ModelAdmin as Django admin does: list_display (methods included), search_fields, list_filter, ordering, readonly_fields. Optional switches add a REST API, MCP tools and search. It is staff-only; graduate a model to a CRUDView of your own when non-staff users need it or you want your own layout.

Which components can I drop onto a page of my own?

Template tags, each one line in a Django template:

  • {% templatetag openblock %} metric_card {% templatetag closeblock %}, {% templatetag openblock %} dashboard {% templatetag closeblock %}, {% templatetag openblock %} goal_list {% templatetag closeblock %}, {% templatetag openblock %} report {% templatetag closeblock %}, {% templatetag openblock %} card {% templatetag closeblock %}: a KPI, a whole dashboard, a goal list, a report or one saved card.
  • {% templatetag openblock %} calendar_card {% templatetag closeblock %}: a calendar of any date-bearing data.
  • {% templatetag openblock %} stat_card {% templatetag closeblock %}: a number tile that opens a drill-down list.
  • {% templatetag openblock %} approval_card {% templatetag closeblock %}: an approval request with its approve and reject buttons, shown only to people allowed to see it.
  • {% templatetag openblock %} help_bubble {% templatetag closeblock %}: an inline explanation linked to a help page.

The dashboards starter shows them on a page (sign in to see it).

Do those components work on my own theme (Bootstrap, Tailwind, a bought theme)?

Yes. Put {% templatetag openblock %} smallstack_assets {% templatetag closeblock %} in your base template's <head> and {% templatetag openblock %} smallstack_modal {% templatetag closeblock %} before </body>. SmallStack's styles load in a CSS cascade layer, so your theme's own rules always win and your page isn't restyled; the components still get the colours and spacing they need. This page is a working example on a stand-in theme.

How do I style a new page so it fits the theme?

Use the theme's CSS variables (--card-bg, --primary, --accent-band-bg, the state colours) and its classes (.card, .table-plain, the buttons), never colour values. Then the page is right on all six palettes in light and dark without extra work. Two rules surprise people: no inline JavaScript (the Content Security Policy blocks it; put scripts in static files), and colours belong in a palette, not on a page. The modern-dark-theme skill is the guide.

How do I put my data on a dashboard or the calendar?

Write a @dataset: a function returning a queryset, plus the columns to expose. It becomes something metrics and dashboard cards can be built from, browsable and exportable, and optionally available over REST and MCP. Give it a start date (and an end date if it has one) with @calendar_dataset and it also appears on the shared calendar with an .ics feed. To ship ready-made metrics and dashboards with your app, declare them in dashboard_defaults.py; they're created after each migrate and never overwrite people's edits.

Can I add my own kind of dashboard card, like a chart or a gauge?

Yes: register_component_type() publishes a card type with its options, its data and its template, using any JavaScript charting library. It then appears in the card builder for people and in the MCP tools for agents. The card-types skill covers it.

How do I add an approval step, a notification or a scheduled job?
  • Approval: declare a kind with @approval_kind and file a request with request_approval(). A person decides in the approvals console (or a {% templatetag openblock %} approval_card {% templatetag closeblock %} on your page), and your code reacts through a callback, a signal, a webhook event or by polling. An AI agent can file a request and wait for a human.
  • Notification: notify(user, …) puts a message in the topbar bell and inbox. It never raises, so a notification can't break the action that sent it. For something that can't wait, send send_branded_email as well.
  • Scheduled job: decorate a function with @scheduled (a cron expression, an interval or a single run). Runs are stored, visible and controllable at /smallstack/scheduler/.
Is there a way to store versioned documents?

The runbook app stores markdown documents with full version history, locking, retention rules and full-text search, readable and writable from the web pages, a service API, REST, MCP and a command line (manage.py rb). It's the base to build on for a knowledge base, policies or anything else that changes over time and needs a record.

How do I control who can see and change what?

In three layers, all applied on every surface:

  • Who may open the pages: mixins, which require a login by default, or [StaffRequiredMixin] for staff only.
  • What each person may do with a model: model_permissions = True checks Django's view, add, change and delete permissions, the ones you grant with groups for Django admin.
  • Which rows: get_list_queryset for what someone may see, and can_update / can_delete / check_object_permission for what they may change.

Creates, edits and deletes are recorded in Django's audit log whichever surface made them.

Integrators

Connecting SmallStack to other tools and systems: scripts, AI assistants, automation platforms and other SmallStack sites.

How does another system call the API?

With a Bearer token. Create one at /smallstack/tokens/ or with manage.py create_api_token, choose read-only or full access, and send it as Authorization: Bearer <token>. The token acts as its user, so that user's permissions and row rules apply. The live schema at /api/schema/openapi.json describes every endpoint, which is what code generators and tools such as Postman read. API Health at /smallstack/api/ shows whether the surface is healthy and who is calling it.

Can Claude or another AI assistant work with my data?

Yes, over MCP (Model Context Protocol) at /mcp. In Claude Desktop or Claude.ai, add it as a custom connector: it signs in through OAuth, so there's nothing to copy by hand. Other MCP clients can use a token. enable_mcp = True on a CRUDView generates list, get, create, update and delete tools for that model; @tool adds tools of your own. Read-only tokens can't call write tools, and every tool applies the caller's permissions and row rules. The dashboards, approvals, runbook, logs and search apps ship their own tools. MCP Health at /smallstack/mcp/ lists what an assistant sees.

How does search work, and can other tools use it?

enable_search = True on a CRUDView adds that model to one ranked full-text index (SQLite's FTS5, or PostgreSQL's full-text search), created automatically when you migrate. It's searched by the topbar search box (Ctrl+K), by a search_… MCP tool per model plus search_all (how an assistant finds things before answering), and by REST at /smallstack/search/api/?q=. Each searcher sees only what they're allowed to see. A model's list page also has its own simpler search box.

Can it notify Zapier, n8n, Slack or my own service when something changes?

Yes. enable_webhooks = True on a CRUDView sends a signed HTTP POST to each endpoint you register whenever a row is created, updated or deleted, however the change was made. Deliveries retry, honour Retry-After, can be replayed from a dead-letter list, and carry a stable event id so the receiver can ignore duplicates. A transform reshapes the body for a target that expects its own format (Slack, CloudEvents, Azure Event Grid).

Inbound works the other way: a receiver at /webhooks/in/<slug>/ verifies the sender's signature (Stripe, GitHub, or a scheme you register) and runs your @webhook_handler. Two SmallStack sites can be paired in one command (sc webhook pair), with protection against an event bouncing back and forth.

Can it publish or read RSS and Atom feeds?

Both. Publish a feed over any queryset you choose (the blog and the status page use this), including podcast-style enclosures. To read one, register_feed_source() pulls an external feed into a model of yours on a schedule.

Can a spreadsheet, a BI tool or a calendar app read my data?

Yes. Every model with an API exports CSV or JSON (?format=csv). Datasets can answer over REST with filters, groups and CSV export. Calendars publish an .ics feed that Google Calendar, Outlook or Apple Calendar can subscribe to, with an API token as the password.

What about scripts and the command line?

manage.py sc (or the sc shim) works on any CRUDView model from a shell: sc ls, get, new, set, rm, with the same validation and audit as the API. --user acts as a given person, with their permissions. It also has operations commands: health checks (sc doctor all), backups, tokens and the search index. Output can be JSON, so it pipes into other tools.

How do I see what's happening on a server I can't log in to?

Warnings and errors are stored in the database and shown at /smallstack/logs/, linked to the request that caused them. When you need more detail you can turn up capture for a set time from that page, from the API or from an assistant. The same records are readable at /api/logger/ and through MCP tools. Request activity (who used what, how fast, which errors) is at /smallstack/activity/, and uptime with a public status page at /status/.

Is it set up for AI coding agents to extend?

Yes. The repository carries AGENTS.md (read by Claude Code, Codex, Cursor, Copilot and Gemini CLI) and a skill file per subsystem, also installed as Agent Skills, so an agent can find the built-in way to do something before inventing its own. The prompts page has copy-ready prompts for common jobs.

Running it

Hosting, data and staying up to date.

Where can I host it?

Anywhere that runs a Docker container. It ships a Dockerfile and Docker Compose setup, and a Kamal configuration that deploys to a single small VPS with HTTPS, a background worker and maintenance windows for deploys. It's an ordinary Django and gunicorn app, so a platform that runs Python web apps works too.

SQLite or PostgreSQL?

SQLite is the default and is tuned for production use (WAL mode, a backup command with retention). PostgreSQL is fully supported, the whole test suite runs on both, and search switches to PostgreSQL's full-text search automatically. Move to PostgreSQL when you have many concurrent writers or want a managed database; there's a documented path to move existing data across.

How do I get SmallStack's updates once I've built on it?

Pull from the upstream repository and merge. Your own code lives in your own apps, so merges mostly touch SmallStack's files. Each release lists what changed in CHANGELOG.md, and anything that needs action on your side has steps in UPGRADING.md.

What does it cost, and what's the licence?

Nothing: it's open source under the MIT licence. Use it for commercial work, change anything, keep your changes private if you want to.
